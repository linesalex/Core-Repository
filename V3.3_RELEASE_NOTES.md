### **API Logs Cleanup Button Fix** 🐛

**Bug Fix:**
Fixed critical bug in Admin Configuration's "Clear Logs Over 8 Days" button that caused backend crashes and prevented log cleanup from functioning.

**What Changed:**
- ✅ Fixed TypeError in database wrapper that prevented access to `this.changes` property
- ✅ Database operations now correctly report number of affected records
- ✅ Log cleanup functionality now works as expected without backend crashes
- ✅ Proper error handling and context passing in database callbacks
- ✅ Fixed secondary issue with automated cleanup trying to log with null user_id
- ✅ Automated system cleanups no longer attempt to log to change_logs (manual cleanups still do)

**Technical Changes:**
- Backend `db.js`:
  - Fixed `run()` method callback to properly pass SQLite statement context using `.call(this, ...)`
  - Changed from `callback(null, this)` to `callback.call(this, null)` for success cases
  - Changed from `callback(err, null, userError)` to `callback.call(this, err, null, userError)` for error cases
  - Ensures callbacks receive proper `this` context with `changes` and `lastID` properties
  - Fixes "Cannot read property 'changes' of undefined" error
- Backend `liveLatencyApiLogsCleanupService.js`:
  - Removed invalid change_logs insert for automated cleanup operations
  - Automated cleanups are system operations without user context
  - Manual administrator-triggered cleanups still log to change_logs (with user_id)
  - Prevents "NOT NULL constraint failed: change_logs.user_id" errors
- Backend `outageHistoryCleanupService.js`:
  - Removed invalid change_logs insert for automated cleanup operations
  - Consistent behavior with live latency API logs cleanup service
- Affects all services using `db.run()`:
  - All route handlers in `routes.js` that check `this.changes` for affected row counts

**Root Cause:**
1. **Primary Issue:** The database wrapper was passing the SQLite statement object as a parameter instead of setting it as the execution context. Callbacks expected to access `this.changes` to determine how many records were affected by DELETE/UPDATE operations, but `this` was undefined, causing the backend to crash with "Cannot read property 'changes' of undefined".
2. **Secondary Issue:** Automated cleanup services were attempting to log system operations to change_logs table with `user_id = null`, but the column has a NOT NULL constraint. This caused "SQLITE_CONSTRAINT: NOT NULL constraint failed" warnings after successful cleanup operations.

**User Impact:**
- Administrators can now successfully use the "Clear Logs Over 8 Days" button in API Admin Configuration
- Backend no longer crashes when attempting log cleanup operations
- No more constraint error warnings in backend logs during automated cleanup
- System maintenance operations function reliably without errors
- Prevents accumulation of old log data
- Improves system stability for automated and manual cleanup tasks
- Manual cleanup operations (triggered by admin) are still logged to change_logs for audit purposes

### **Bandwidth Filtering - 2x Requirement Rule** ⚡

**Critical Change:**
Changed bandwidth filtering logic to require **double (2x) the requested bandwidth** for a circuit to be considered in path finding.

**What Changed:**
- ✅ **Before**: Request 2000 Mbps → Need ≥2000 Mbps circuits
- ✅ **After**: Request 2000 Mbps → Need ≥4000 Mbps circuits
- ✅ **Formula**: Required Circuit Bandwidth = Requested Bandwidth × 2
- ✅ Prevents over-utilization of circuits
- ✅ Ensures adequate capacity headroom

**Examples:**
- Request 1000 Mbps → Need circuits with ≥2000 Mbps
- Request 2000 Mbps → Need circuits with ≥4000 Mbps
- Request 5000 Mbps → Need circuits with ≥10000 Mbps
- Request 10000 Mbps → Need circuits with ≥20000 Mbps

**Technical Changes:**
- Backend filters circuits: `Route Bandwidth >= (Requested × 2)`
- Applies to **Auto Design** path finding
- Applies to **Manual Design** route suggestions ("Find Suggestions")
- Enhanced logging shows both required and requested bandwidth
- Exclusion reasons track both values for troubleshooting

**User Impact:**
- More conservative route selection
- Better capacity planning
- Reduces risk of circuit congestion
- May find fewer available paths (by design)
- Ensures 50% maximum utilization per circuit
